The core BuildCustom hosting system is now working:

- BuildCustom can generate a real application through the VibeSDK/ThinkAgent runtime.
- The generated application can be previewed.
- It can be published through our Cloudflare/Workers for Platforms hosting infrastructure.
- The application is publicly accessible on our BuildCustom-hosted subdomain.
- Assets including favicons and social sharing images are working.
- We have now begun proving customer-owned custom domains using Cloudflare for SaaS / Custom Hostnames.

During testing we discovered an important real-world onboarding issue:

A customer may want to connect:

buyermagnets.com

but their existing DNS provider may not allow a normal CNAME at the zone apex/root because other records such as A, MX, TXT, etc. already exist.

We do NOT want to require Cloudflare Enterprise / Apex Proxying for BuildCustom V1.

Instead, I want BuildCustom to have a simple, safe domain connection wizard that supports BOTH:

PATH A:
Keep the customer's existing DNS provider and connect a hostname such as:

www.customer.com → CNAME → fallback.buildcustom.ai

or use the root domain when their DNS provider natively supports ALIAS, ANAME, apex CNAME flattening, or an equivalent capability.

PATH B:
For customers whose DNS provider cannot connect the root domain properly, recommend moving ONLY authoritative DNS management to Cloudflare DNS.

This is NOT a domain registrar transfer.

The customer continues owning and renewing their domain through their existing registrar. Only the authoritative nameservers change to Cloudflare.

Once Cloudflare is authoritative, Cloudflare's apex CNAME flattening can allow the root domain to connect to BuildCustom without requiring BuildCustom to purchase Enterprise Apex Proxying.

IMPORTANT:

We are going to test this workflow using an owned test domain.

Do NOT disrupt the existing working BuildCustom hosting architecture.

Do NOT modify or remove the existing Workers for Platforms deployment path.

Do NOT modify legacy Cloudflare resources unless explicitly required and approved.

Do NOT purchase, transfer, or move domain registration.

Do NOT automatically change registrar nameservers.

Do NOT delete existing DNS records.

Do NOT guess Cloudflare IP addresses.

Do NOT implement Enterprise Apex Proxying.

Do NOT make destructive DNS changes without explicit confirmation.

Do NOT expose Cloudflare API credentials to the browser.

The goal is to build the minimum real production-quality Domain Connection Wizard necessary to safely test this complete workflow.

3. CLOUDFLARE DNS SETUP WIZARD
==================================================

Create a guided Cloudflare DNS migration wizard.

This wizard must clearly explain:

"You are NOT transferring your domain.

Your domain stays registered with your current registrar. You are only changing which service manages its DNS records."

The wizard should have clearly separated steps.


STEP 1:
Inspect Existing DNS

Before telling the customer to change nameservers, BuildCustom should perform a read-only DNS inventory using appropriate server-side DNS resolution.

Attempt to discover existing records including, where available:

A
AAAA
CNAME
MX
TXT
CAA
SRV
NS

Also specifically look for records commonly associated with email and authentication:

MX
SPF
DKIM
DMARC

Display the discovered records in a readable table.

Do not pretend DNS discovery is guaranteed to find every private/provider-specific record.

Show a warning:

"We found these public DNS records. Before changing nameservers, compare them with the DNS records shown by your current DNS provider. Missing email or verification records can interrupt services."

The system should NEVER claim the scan guarantees completeness.


STEP 2:
Prepare Cloudflare Zone

Determine whether the domain already exists as a zone in the BuildCustom-controlled Cloudflare environment.

For THIS TEST / CURRENT ARCHITECTURE:

Do not automatically create or mutate a Cloudflare zone until you have first inspected the available Cloudflare APIs, permissions, account boundaries, and existing architecture.

Before implementing automatic zone creation, report whether managing customer DNS zones inside the BuildCustom Cloudflare account is actually the architecture we should use.

This is important.

We need to distinguish between:

A) customers creating/managing their own free Cloudflare account and BuildCustom guiding them

versus

B) BuildCustom creating/managing customer DNS zones inside our Cloudflare account.

Do not silently choose B just because our API token can create zones.

Evaluate security, ownership, operational responsibility, account limits, customer portability, API capability, and whether Cloudflare permits the intended SaaS architecture.

For the immediate owned-domain test, use the safest architecture that can later scale appropriately.

If manual Cloudflare onboarding is safer for V1, the wizard may guide the customer through creating a free Cloudflare account and adding their domain rather than BuildCustom owning their DNS zone.


STEP 3:
DNS RECORD SAFETY CHECK

Before nameservers are changed, create a checklist comparing:

Existing publicly discovered DNS records

versus

records expected in Cloudflare.

Highlight especially:

MX
SPF
DKIM
DMARC
TXT verification records
mail hostnames
other subdomains

Use clear warnings for potentially missing records.

Examples:

"Email records detected"

"MX records detected"

"SPF record detected"

"DMARC record detected"

"DKIM record may require manual verification"

"Additional TXT verification records detected"

If the domain appears to use email, display a prominent warning:

"Changing nameservers before your email DNS records are present in Cloudflare could interrupt email."

Require an explicit checkbox:

"I have reviewed my DNS records and understand that missing records can affect email or other services."

Do not allow the wizard to proceed to nameserver switching instructions without this acknowledgement.


STEP 4:
CHANGE NAMESERVERS

Once the DNS safety check is complete, show:

"Change your domain's nameservers"

Explain:

"Go to the company where your domain is registered and replace the current nameservers with the Cloudflare nameservers shown below."

Show the actual Cloudflare-assigned nameservers if they are available through the architecture we choose.

Example UI:

A2 Hosting

Current nameservers:
ns1.example.com
ns2.example.com

New Cloudflare nameservers:
xxxx.ns.cloudflare.com
yyyy.ns.cloudflare.com

[Copy]

Do NOT attempt to log into or modify the customer's registrar.

The customer makes this change themselves.


STEP 5:
VERIFY NAMESERVER CHANGE

BuildCustom should periodically or manually check authoritative NS records.

Provide:

Check Again

When the expected Cloudflare nameservers become authoritative, update:

Waiting for Nameservers

to:

Cloudflare DNS Active

Do not rely only on browser state.

Verification must happen server-side.
