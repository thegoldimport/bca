==================================================

==================================================
STEP 4 — RESET TOKEN SECURITY
==================================================

Use cryptographically secure random reset tokens.

Requirements:

- high entropy
- single use
- short expiration
- tied to the correct runtime user
- cannot be reused after successful reset
- expired tokens rejected
- invalid tokens rejected
- token cannot reset another account


Prefer storing only a HASH of the reset token if compatible with the existing
schema/design.

Do not store plaintext reset tokens unnecessarily.


A reasonable expiration is:

30–60 minutes.


Use the existing schema's intended expiration behavior if already defined.

STEP 6 — RESET PASSWORD ENDPOINT
==================================================

Implement the reset endpoint using existing runtime password hashing and
validation.

Conceptually:

POST /api/auth/reset-password


Input:

token

newPassword


Require the same password-strength rules used by registration.


On valid token:

1. verify token securely

2. verify not expired

3. verify unused

4. identify runtime user

5. hash new password using EXISTING runtime password hashing

6. update that SAME runtime identity

7. invalidate/consume reset token

8. revoke existing active sessions for that account as appropriate for secure
   password reset

9. return bounded success response


Do NOT create another user.

Do NOT modify BuildCustom product identity.

Do NOT create local BuildCustom password authority.
