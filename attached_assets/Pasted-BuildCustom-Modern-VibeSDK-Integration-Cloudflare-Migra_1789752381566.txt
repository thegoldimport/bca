BuildCustom: Modern VibeSDK Integration + Cloudflare Migration Plan

Product context

BuildCustom.ai is intended to be a full AI app-building platform similar in experience to Replit.

A normal user should be able to log into BuildCustom, open a project, talk to the built-in coding agent, have it create or modify a real application, see a live preview, continue editing conversationally, and deploy the finished application.

The native BuildCustom coding agent should be the current VibeSDK agent/runtime branded and presented as BuildCustom. We do NOT want to build another coding agent in front of VibeSDK.

To the customer it is simply:

User → BuildCustom chat → VibeSDK-powered coding agent/runtime → preview → deployment.

Later, advanced users should be able to bypass the native agent and use Claude Code, Codex, Hermes, OpenClaw, etc. through BuildCustom MCP/API/CLI access to the same underlying project/runtime/deployment capabilities.

Do NOT design:

Claude Code → BuildCustom agent → VibeSDK agent.

Claude Code is already an agent. Eventually it should access BuildCustom's underlying capabilities directly.

Critical infrastructure requirement

We want BuildCustom off Replit as soon as practical.

Replit is currently being used because the existing BuildCustom application was developed here. Replit is a temporary development environment during the migration, not part of the desired production architecture.

When making architectural decisions, favor approaches that reduce our dependency on Replit rather than deepen it.

The desired end state is:

Deleting this Replit project would have zero effect on BuildCustom or any customer application.

Do not introduce new permanent dependencies on Replit hosting, Replit databases, Replit deployment infrastructure, Replit object storage, or Replit-specific services unless absolutely necessary for the temporary migration.

Domain model

Keep:

buildcustom.ai = public sales/marketing website

app.buildcustom.ai = logged-in BuildCustom dashboard, builder, project UI and native coding-agent experience

Generated apps should NOT use the old ambiguous domain architecture where app.buildcustom.ai can be interpreted as an app named app.

Design separate hostname responsibilities for:

BuildCustom product
internal runtime if necessary
temporary previews
BuildCustom-hosted production applications
customer custom domains

For example, preview applications could eventually use something like:

<id>.preview.buildcustom.ai

Do not assume that exact naming is required. Recommend the cleanest architecture.
