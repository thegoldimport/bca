==================================================
PART 1 — NON-INTERFERENCE REQUIREMENT
==================================================

Diagnostic instrumentation must be BEST-EFFORT ONLY.

It must be impossible for diagnostic collection, formatting, serialization,
redaction, or persistence to:

- replace the original exception
- suppress the original exception
- prevent an existing callback
- prevent an existing finally/cleanup path
- alter success into failure
- alter failure into success
- alter cancellation behavior
- alter continuation behavior
- alter WebSocket behavior
- alter RPC behavior
- alter tool behavior
- alter operation state
- alter completion behavior

The original application behavior always wins.

==================================================
SAFE DIAGNOSTIC PATTERN
==================================================

Implement a small safe diagnostic boundary.

Conceptually:

try {
    bestEffortDiagnostic(...)
} catch {
    // diagnostics are dropped
}

But implement it cleanly for the existing architecture.

Any metadata producer/factory/getter must execute INSIDE that protected
diagnostic boundary.

Do not evaluate diagnostic metadata before entering the safety boundary.

This includes:

- lazy metadata factories
- getters
- stack extraction
- cause extraction
- JSON serialization
- redaction
- persistence/logging
- WebSocket metadata
- RPC metadata
- tool metadata
- operation metadata

If ANY diagnostic step fails:

DROP THAT DIAGNOSTIC EVENT OR FIELD.

Continue the original application/error path unchanged.

==================================================
ORIGINAL ERROR PRESERVATION
==================================================

Where instrumentation surrounds an existing error path:

capture best-effort diagnostics

then preserve EXACT existing behavior.

Do not:

Do not wrap merely for diagnostics.

Do not replace cause chains.

Do not convert cancellation into another exception type.

PART 3 — ERROR TEXT
==================================================

We still need enough information to identify the original failure.

Use a SAFE representation.

Prefer:

- error constructor/name from a bounded known representation
- stable error code where available
- internal source file/function where derivable safely
- sanitized stack frames
- cause TYPE/classification
- nested cause TYPE/classification

Do NOT blindly persist arbitrary:

error.message
error.stack
cause.message
WebSocket reason

because they may contain user input or credentials.

If retaining message text is necessary for diagnosis:

use a strict bounded sanitizer.

Requirements:

- hard maximum length
- remove control characters
- redact obvious authorization/token/key/password/email/URL query material
- redact high-entropy credential-like substrings
- redact JWT-like strings
- redact bearer/basic authorization material
- redact cookie material
- redact query-string secrets
- redact UUID/session/token values where not already represented in approved
  structured fields
- fail closed

If sanitizer is uncertain or throws:

store:

"[REDACTED]"

or omit the field.

Do not allow sanitization failure to affect the original application path.

Do not affect the original error.
