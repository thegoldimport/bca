==================================================
WHY WE ARE CHANGING THIS
==================================================

BuildCustom currently allows one customer request to perform a bounded amount
of autonomous work.

Current operation limits are intentionally:

maxSteps per Think pass = 25
Think turns = 5
maxContinuations = 4
maxCredits = 250
maxElapsedMs = 900000

Those limits are GOOD.

We do NOT want an agent getting stuck and autonomously burning unlimited model
calls, time, or money.

However, when the agent reaches one of those autonomous-work limits while the
customer's task is still unfinished, the current customer experience is wrong.

Project 8 demonstrated this.

The agent made substantial progress but eventually ended:

INCOMPLETE_RESOURCE_LIMIT
reason: continuation_budget_exhausted

That internal reason is useful for BuildCustom diagnostics.

It is NOT useful customer-facing language.

The customer should not need to understand:

- Think turns
- continuation budgets
- model-call budgets
- internal credits
- resource limits
- INCOMPLETE_RESOURCE_LIMIT
- continuation_budget_exhausted

From the customer's perspective:

"The agent worked for a while, made progress, but there is still more work to
do."

BuildCustom should ask permission to continue.

==================================================
PRODUCT MODEL
==================================================

We need to distinguish THREE concepts.

1. TASK

The overall thing the customer asked BuildCustom to accomplish.

Example:

"Fix the CRM so data persists, Activity Timeline works, and Recent Activity is
correct."

A task may require multiple bounded work sessions.

The task survives across those work sessions until:

- completed
- customer stops it
- customer changes direction
- genuinely blocked waiting for customer information/action

--------------------------------------------------

2. OPERATION / WORK SESSION

One bounded autonomous coding session.

Each operation receives the existing limits:

25 steps per Think pass
5 Think turns
4 automatic internal continuations
250 credits
15 minutes

When that operation reaches its allowed autonomous-work boundary, BuildCustom
does NOT automatically give it unlimited additional budget.

If work remains, return control to the customer.

--------------------------------------------------

3. INTERNAL CONTINUATION

These are the existing automatic continuations inside ONE operation.

They share the SAME:

- operation identity
- resource counters
- elapsed timer
- credit budget
- task/progress state

Do not change that behavior.

==================================================
NEW CONCEPT: USER-APPROVED CONTINUATION
==================================================

When an operation reaches its autonomous-work limit but the TASK is unfinished,
BuildCustom should present:

"I made progress, but there's still more to finish."

Then summarize:

WHAT I COMPLETED

and

WHAT'S STILL LEFT

Then ask:

"Continue working?"

Provide a clear:

Continue

action.

The customer may also respond conversationally with things such as:

yes
continue
keep going
go ahead
finish it
keep working

A user-approved continuation means:

SAME TASK
SAME ORIGINAL CUSTOMER INTENT
SAME CONVERSATION
SAME PROJECT
SAME AGENT
SAME WORKSPACE
SAME FILES
SAME GIT HISTORY
SAME CURRENT REVISION
SAME PROGRESS

but:

NEW OPERATION / WORK SESSION
NEW bounded resource allowance

The new operation receives fresh:

- credits
- Think-turn count
- internal-continuation count
- elapsed timer
- operation-scoped model-call count
- operation-scoped tool-call count
- operation-scoped resource state

Configured ceilings remain unchanged.

==================================================
CRITICAL SEMANTICS
==================================================

USER-APPROVED CONTINUATION MUST NOT:

- resend the original customer instruction as a new unrelated request
- make the model rediscover the task from scratch
- create another project
- create another workspace
- reset files
- reset Git history
- discard progress
- duplicate completed work
- erase conversation history
- silently grant unlimited autonomous work

Instead it should mean:

"Continue this existing unfinished task from the current state with another
bounded work session."

==================================================
TASK IDENTITY VS OPERATION IDENTITY
==================================================

Implement/extend the lifecycle so that one TASK can own multiple OPERATIONS.

Conceptually:

Task T1
    Operation O1
        internal pass
        internal continuation
        internal continuation
        limit reached

    customer approves Continue

    Operation O2
        internal pass
        internal continuation
        ...

    customer approves Continue

    Operation O3
        ...

    COMPLETE

The exact implementation does not need these literal names if the existing
architecture already has appropriate identities.

Reuse existing concepts wherever possible.

Do NOT build a competing orchestration system.

Do NOT replace the native ThinkAgent.

Do NOT duplicate workspace state.

This should be the smallest extension of the current task/operation lifecycle.

==================================================
WHEN TO OFFER CONTINUE
==================================================

Offer customer continuation when:

1. the operation reached a bounded autonomous-work limit

AND

2. the overall task is not established COMPLETE

AND

3. the system does not require some specific missing customer input

Examples include appropriate internal reasons such as:

continuation_budget_exhausted

Think-turn/work-session exhaustion

credit allowance exhausted for THIS operation

elapsed-time allowance exhausted for THIS operation

other equivalent bounded autonomous-work limits

Do NOT automatically expose those reasons to the customer.

Keep them internally for diagnostics.

==================================================
WHEN NOT TO OFFER CONTINUE
==================================================

Do NOT show generic Continue when:

TASK COMPLETE

Show:

Build complete

--------------------------------------------------

ACTUAL CUSTOMER INPUT REQUIRED

Example:

"I need your Stripe secret key before I can test checkout."

Show something like:

Needs your input

and explain what is required.

--------------------------------------------------

SECURITY / OWNERSHIP FAILURE

Do not turn that into Continue.

--------------------------------------------------

UNRECOVERABLE PLATFORM FAILURE

Do not pretend that more agent work will solve infrastructure corruption.

--------------------------------------------------

CUSTOMER CANCELLED

Do not continue.

==================================================
CUSTOMER-FACING STATES
==================================================

Simplify the normal customer experience to three major outcomes.

--------------------------------------------------

1. BUILD COMPLETE

Use green success state only when the task is actually established complete.

Example:

✓ Build complete

"Your changes are ready to review."

Do NOT show this when supported lifecycle is:

BLOCKED

INCOMPLETE_RESOURCE_LIMIT

RUNNING

RECOVERING

VERIFYING

USER_INPUT_REQUIRED

or any other unfinished state.

This also addresses the issue we observed where the editor displayed a green:

Build complete

while supported lifecycle was:

BLOCKED

That is misleading and should be corrected as part of this lifecycle/UI work.

--------------------------------------------------

2. CONTINUE?

Use when the agent made progress but exhausted the current bounded work session
while the task remains unfinished.

Example:

"I made progress, but there's still more to finish.

Completed:
• Dashboard and lead list are working
• Search, sorting, and filtering are working
• Recent Activity is displaying

Still working on:
• Saving lead changes correctly
• Note persistence
• Activity Timeline

Continue working?"

[ Continue ]

Do NOT show:

insufficient tokens

insufficient turns

continuation budget exhausted

available credits limit

INCOMPLETE_RESOURCE_LIMIT

elapsed_time_limit

or other internal lifecycle terminology to normal customers.

Those remain available in diagnostics/admin/support surfaces.

--------------------------------------------------

3. NEEDS YOUR INPUT

Use when progress cannot continue without information/action from the customer.

Example:

"I need your Stripe API key before I can test checkout."

Do not present this as an autonomous-work exhaustion.

==================================================
PROGRESS SUMMARY
==================================================

The continuation message should summarize actual known progress.

Do NOT fabricate accomplishments.

Use the best existing trustworthy information available from:

- task progress
- completed agent work
- tool results
- verification results
- current revision/workspace
- completion state

If detailed structured progress is unavailable, use a conservative message:

"I made progress on your request, but I haven't finished everything yet.

Would you like me to continue working?"

That is acceptable.

Do NOT require another model call solely to create fancy continuation copy if
doing so would defeat the purpose of stopping at the operation boundary.

==================================================
CONTINUE BUTTON
==================================================

Add a normal customer-facing Continue action.

When clicked:

1. verify the task still belongs to the authenticated customer
2. verify the task remains unfinished
3. verify no operation is currently RUNNING
4. verify continuation is eligible
5. create/start the next bounded operation for the SAME TASK
6. preserve workspace/current revision/progress
7. give the new operation fresh operation-scoped counters
8. continue the original task

The button must be idempotent.

Double-clicking or retrying the request must NOT start two operations.

If an operation is already running for that task, another Continue request
must not create another concurrent operation.

==================================================
CONVERSATIONAL CONTINUE
==================================================

The user should also be able to type:

yes

continue

keep going

go ahead

finish it

etc.

when the current task is specifically waiting for continuation approval.

Do NOT globally interpret every "yes" as continuation.

Only interpret it this way when:

- there is a current unfinished task
- it is explicitly awaiting continuation approval
- there is no conflicting newer customer task/message

Prefer using the same underlying continuation action as the Continue button.

Do not implement two separate continuation systems.

==================================================
NEW CUSTOMER REQUEST WHILE CONTINUE IS OFFERED
==================================================

This is important.

If BuildCustom is asking:

"Continue working?"

and instead the customer sends a NEW substantive instruction such as:

"Actually forget that, add a settings page instead."

Do NOT automatically continue the old task.

Treat the new substantive customer instruction according to the existing
new-message/task behavior.

The old task should no longer silently consume work sessions.

Preserve its history.

==================================================
FRESH OPERATION ACCOUNTING
==================================================

For each USER-APPROVED continuation operation initialize fresh:

credits used = 0

Think turns used = 0

internal continuations used = 0

operation elapsed timer = now

operation-scoped model/tool counters = fresh

operation terminal/resource-limit reason = none

But preserve TASK-level information including:

- original intent
- task identity
- prior operation history
- progress
- current workspace
- current revision
- relevant verification state
- conversation context

Do not accidentally reset the task itself.

==================================================
LIMIT LOOP
==================================================

This may happen repeatedly.

Operation O1 reaches boundary.

Continue?

Customer approves.

O2 reaches boundary.

Continue?

Customer approves.

O3 completes.

Build complete.

That is valid.

Do NOT impose an arbitrary task-wide number of customer-approved work sessions
unless the platform already has a deliberate account-level usage/billing limit.

Any real account-level billing/usage restriction should remain separate from
these per-operation autonomous-work limits.

Do not bypass genuine account billing restrictions.
