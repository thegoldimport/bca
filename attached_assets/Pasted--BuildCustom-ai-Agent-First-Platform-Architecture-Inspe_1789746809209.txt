# 1. ORIGINAL BUILDCUSTOM.AI VISION

BuildCustom.ai was originally being built as an AI software development platform similar in concept to Replit.

It was NOT originally intended to be merely:

* a website builder
* a landing-page builder
* a hosting company
* a code generator

The larger vision was:

> **Tell AI what you want to build, let AI build it, and deploy it without leaving BuildCustom.**

We had already started building infrastructure around Cloudflare because we wanted applications created inside BuildCustom to be deployable onto our own underlying infrastructure.

Cloudflare would effectively be infrastructure underneath BuildCustom.

The customer should interact with:

**BuildCustom**

not:

**Cloudflare**

The intended experience was approximately:

USER

↓

BUILDCUSTOM AI

↓

AI CREATES APPLICATION

↓

LIVE PREVIEW

↓

USER TALKS TO AI TO MAKE CHANGES

↓

AI BUILDS / TESTS / FIXES

↓

USER TELLS AI TO DEPLOY

↓

BUILDCUSTOM DEPLOYS APPLICATION

↓

CLOUDFLARE INFRASTRUCTURE

↓

LIVE APPLICATION

We never completely finished this system.

---

# 2. UPDATED VISION: BUILDCUSTOM SHOULD BE AGENT-FIRST

We now want to push the original concept further.

BuildCustom should be an:

# AGENT-FIRST AI BUILDING + DEPLOYMENT PLATFORM

The primary interface should be an AI agent.

The user should NOT have to understand:

* coding
* Git
* deployments
* DNS
* Cloudflare
* Workers
* servers
* build commands
* package managers
* SSL
* infrastructure configuration

The user should be able to talk naturally to an AI agent.

For example:

> Build me a landing page for my roofing company.

The BuildCustom agent builds it.

Then:

> Make the hero darker and add a quote form.

The agent modifies it.

Then:

> Connect the form to my CRM.

The agent handles that if the necessary integration exists.

Then:

> Put this online.

The agent deploys it.

Then:

> I own roofingexample.com. Connect that domain.

The agent walks the user through or performs as much of the domain setup as BuildCustom can safely automate.

The user should be able to operate nearly the entire BuildCustom platform conversationally.

# 4. EXTERNAL AGENTS ARE A CORE PART OF THE VISION

This is another major requirement.

We do NOT want BuildCustom to force every advanced user to use only the native BuildCustom agent.

Many developers and AI builders already prefer agents such as:

* Claude Code
* Codex
* Hermes
* OpenClaw
* other current/future coding agents

We want BuildCustom to eventually expose an agent-friendly interface so these external agents can operate BuildCustom on the user's behalf.

Conceptually:

CLAUDE CODE

↓

BUILDCUSTOM AGENT/API/MCP INTERFACE

↓

CREATE PROJECT

↓

UPLOAD/MODIFY FILES

↓

BUILD

↓

PREVIEW

↓

DEPLOY

↓

CONFIGURE DOMAIN

↓

MANAGE APPLICATION

The same should be possible with Codex, Hermes, OpenClaw, or another sufficiently capable agent.

The customer could therefore choose between:

### OPTION A — BUILDCUSTOM AGENT

Open BuildCustom.ai and simply talk to our native agent.

OR:

### OPTION B — BRING YOUR OWN AGENT

Connect an external agent they already use and allow that agent to operate BuildCustom for them.

This means the architecture should NOT tightly couple all platform functionality to our chat UI.

Core BuildCustom capabilities should eventually be exposed as secure tools/actions that can be invoked by:

* BuildCustom's native agent
* BuildCustom's UI
* BuildCustom API clients
* MCP or another agent protocol
* Claude Code
* Codex
* Hermes
* OpenClaw
* future agents

This is an important architectural principle.
