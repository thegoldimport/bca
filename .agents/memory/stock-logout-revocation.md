---
name: Stock runtime logout revocation
description: Why a successful logout response is insufficient evidence of revoked VibeSDK sessions.
---

For a clean stock VibeSDK runtime, require a post-logout request using the **pre-logout** credential to fail. HTTP 200 from logout, a cleared browser cookie, or a successful new login is not sufficient evidence of session revocation. The pinned launch runtime includes an accepted owner-scoped revocation patch; the unpatched stock logout did not receive the sessionId cookie it expected. Require token subject and stored session owner to agree, and confirm owner-scoped revocation changed the stored session rather than silently updating zero rows.

**Why:** Private acceptance of unpatched stock auth found old credentials still valid after logout. A later public-gate check falsely reported recurrence because it checked HTTP status only: both product and runtime `/api/auth/me` can return **200 with JSON null** for an anonymous request, and runtime `/api/auth/check` returns 200 with `authenticated: false`. A controlled replay of the accepted launch runtime confirmed the exact old session row changed from active to revoked, the old credential no longer resolved an identity at either origin, and independent sessions remained valid. A security review also found that an owner-scoped database update can silently affect zero rows if token subject and session owner disagree. In a separate signup launch, logout returned 204 and the session row was revoked, but browser-response/cookie checks halted acceptance before old-credential replay. That is incomplete evidence, not proof of a revocation defect.

**How to apply:** Before asserting launch auth acceptance, compare authenticated identity (`null` versus user, or `/api/auth/check` authenticated boolean), not status alone, and verify the session's server-side revocation state. Replay the pre-logout credential even if the response body cannot be read or browser-cookie observation is inconclusive; if replay cannot be completed, fail closed without claiming a proven runtime defect. Include missing/mismatched/no-op row tests. Do not patch a locked stock+approved-patch baseline based only on a 200 status; distinguish patched launch runtime from an unpatched stock checkout.
