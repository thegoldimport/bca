---
name: Runtime cutover capability disagreement
description: Guarded production runtime activation yielded a false live registration capability despite correct version and binding checks.
---

In a single guarded public-signup activation, deployment readback showed the intended runtime version at 100% and the old version at 0%. The candidate configuration recheck had shown registration enabled, but both a targeted version-override capability request and an ordinary live capability request failed the required `registrationEnabled=true` observation. Existing-user authentication passed. The runtime was restored to the closed version without activating the control candidate or retrying.

**Why:** Cloudflare deployment and binding readbacks alone did not prove the live runtime capability. The preserved operator journal summarized failed checks but not raw responses or per-request versions, so its exact cause remains unknown. For this container/Durable Object Worker, Cloudflare reported no Version URL, and version overrides require the target in the current deployment. Tail correlation once missed an ordinary closed request despite a matching nearby targeted event. A later separately authorized, guarded runtime-only diagnostic correlated both candidate requests to the candidate itself and observed correct registration capability and existing-user auth; it then restored the closed runtime. That establishes current candidate reusability, not why the earlier attempt failed.

**How to apply:** Keep candidate configuration, targeted capability, and ordinary live capability as separate required gates. Redact CSRF tokens and cookies from capability responses, but capture safe response details and correlate each request to a tail version. Treat missing per-request tail as UNKNOWN and fail closed, even if a nearby request correlated. Do not infer an earlier failure's cause from a later pass, or reuse a prior activation authorization. A final signup cutover requires its own permission and closed-state precheck.
