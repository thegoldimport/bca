---
name: Cloudflare module uploads
description: Multipart requirements for safely updating an existing Cloudflare module Worker.
---

For module-format Worker uploads, set `main_module` in multipart metadata and give the JavaScript file part that exact filename. Preserve the existing bindings explicitly in the upload metadata. For the versions API, `inherit` bindings accept only the literal `version_id: "latest"`; a pinned UUID is rejected even when it is the currently serving version. Check the serving version immediately before upload and compare the new version's resources before deployment.

After deploying an older version for cleanup, do not assume script-level settings describe the serving version's bindings. Check the active deployment's version resources directly. Script-level settings can still expose a temporary secret from the latest *inactive* uploaded version, even when the active older version has neither that binding nor the diagnostic route. The script-level secret-delete API can reject the deletion with 10215 because the latest version is not currently deployed; do not redeploy the diagnostic version just to satisfy that API without separate authorization.

**Why:** Cloudflare returns validation error 10021 (“No such module”) when the form field is named like the module but its uploaded filename does not match `main_module`. It also rejects JavaScript imports with “Cannot use import statement outside a module” unless module parts use `application/javascript+module`. Replacing a script without its current bindings can disconnect KV or dispatch namespaces. Downloaded Workers can contain binary WASM parts; text-decoding and re-encoding their multipart response corrupts the bytes. A prior rollback deployment left the active version clean but the settings endpoint still showed a secret added only to an inactive version.

**How to apply:** Read the existing Worker settings first, reuse its bindings and compatibility date, and preserve every original module as bytes, changing only the intended JavaScript part. Upload with the module MIME type and a multipart filename that exactly matches `main_module`; verify parity before activating the uploaded version. For post-rollback cleanup, compare the serving version's resources to script settings before claiming a secret is active or removed.

For historical source comparisons, do not treat `content/v2?version_id=...` as a version-specific download: the unsupported query parameter is ignored and the latest uploaded bundle is returned. The legacy script-version detail endpoint exposes metadata, not module bytes; appending `/content` also returns version metadata. The separate Workers API endpoint `/workers/workers/{worker_id}/versions/{version_id}?include=modules` returns that historical version's base64-encoded modules. Normalize optional `./` prefixes before comparing module names and hash decoded bytes rather than comparing script ETags, which also change with bindings. **Why:** An ignored selector can falsely attribute the latest source to an old version; conversely, a different ETag need not mean changed code. **How to apply:** Use the version-specific modules response for byte-level provenance, then independently compare bindings, assets, and container configuration before deploying.

For a public binding-only cutover, prefer an explicitly inactive version upload using the serving module's exact bytes, followed by a separate deployment, rather than assuming the script-settings PATCH stages without changing traffic.

**Why:** Cloudflare documents version upload as non-deploying, but the settings PATCH does not promise the same behavior. A local gateway source file can also differ from the serving bundle. Capturing the live multipart module only when the latest uploaded version is the active one and its download ETag matches the active script fingerprint gives a defensible code-identity check.

**How to apply:** Snapshot the active version and all bindings, verify that source identity, stage the byte-identical module with changed bindings, then compare the new version's script/runtime resources and confirm the old deployment still serves 100% before deploying the new one. Keep the old version intact for a single exact-version rollback deployment.

For an asset-backed Worker, a full-binding-list script-settings PATCH was observed to create and immediately deploy a new version at 100%. Treat this endpoint as a live cutover rather than an inactive staging operation.

**Why:** An upload-only version attempt with inherited bindings returned an internal Cloudflare error without creating a version. The subsequent settings PATCH preserved the source bytes and asset runtime but activated the new flag immediately. After the previous version was redeployed for rollback, script-level settings still reported the flag from the latest inactive version, while the serving version and public capability correctly reported the old value.

**How to apply:** Prepare an exact old-version deployment rollback before a settings PATCH; send the complete binding inventory, inspect the active deployment and effective version resources immediately, and verify source bytes plus assets. After rollback, read the active version and public behavior for the effective flag, not script-level settings alone. Account for the newer inactive version before future deployments or binding inheritance.

For an asset-backed Worker, inheriting its `ASSETS` binding in a raw multipart version upload does not necessarily preserve `script_runtime.assets`. A candidate can retain every binding and byte-identical modules yet lose its SPA/asset-serving configuration. An exact-module Wrangler `--no-bundle` version upload with the existing asset directory can preserve that runtime configuration without rebuilding application code. Verify all module bytes and the full `script_runtime` shape before traffic; module fingerprint equality alone is insufficient.

**Why:** A binding-only candidate inherited `ASSETS` but omitted the accepted asset-serving settings. Repacking the accepted module bytes through Wrangler preserved assets; its version metadata also made the existing container application's name explicit, so a different script fingerprint by itself did not establish a source-code change.

**How to apply:** Keep a known serving version available for rollback, stage candidates inactive, compare module names and hashes as well as binding and runtime-resource parity, and verify static assets were not reuploaded unexpectedly. Treat a container-name metadata difference separately from a real container configuration change.
