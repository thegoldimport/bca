---
name: Single-use browser acceptance
description: Safely exercise one-time dashboard operations when a browser automation input may not update application state.
---

For a single-use browser action, checkpoint before the mutation and distinguish a pre-click UI failure from an unknown post-click outcome. Do not retry from an ambiguous checkpoint. A controlled input can display the filled text while React submit state remains stale; verify both the displayed value and the application's submitted state before clicking. If the unique marker is absent after a click, an ordinary application GET with no match cannot prove zero side effects: the app may have saved different values. An authoritative storage inspection of IDs, timestamps, and known seed rows can settle whether a mutation persisted, but it cannot reconstruct an unrecorded OPTIONS or POST.

**Why:** One private acceptance run timed out before a create click because the visible field had the expected text but its submit control stayed disabled. Another reached a single Add Lead click, but the marker appeared in neither the UI nor a subsequent collection; later inspection of the actual app storage showed only the original seed rows, resolving the persisted-insert question without proving where the request stopped. A later pre-click guard aborted correctly after normal browser typing, but its combined assertion did not retain which field check failed. Even a valid, enabled form can accept one browser click without an observed lead request or persisted row; click completion alone does not prove a network submission. A separately authorized instrumented click captured the missing cause: Chromium blocked submission in a sandboxed preview lacking `allow-forms` before firing a submit event, despite correct React-controlled field values.

**How to apply:** In future one-shot UI provisioning tests, make the checkpoint represent the actual mutation boundary. Persist named, non-sensitive form-check results before the pre-click assertion, and sanitized request evidence after a click even on failure. If a pre-click attempt fails, verify authoritative storage before resuming. For controlled numeric inputs, identify the field by its rendered label and replace selected text without first clearing it; this browser driver rejects a combined `Control+A` press, so send Control-down, `a`, and Control-up separately. Capture full console output and click/submit events before any one-shot click; an iframe sandbox without `allow-forms` can prevent React's submit handler from running at all. If the click may have happened, inspect storage read-only and report transport and persistence separately; do not clear the no-retry guard or perform another mutation without explicit approval.

For chat editors, the submission boundary can occur during text entry, not just at the planned Send click. Multiline keyboard typing can turn the first newline into Enter-to-submit. Use multiline text insertion without Enter key presses, and attach outbound-instruction observers before filling the composer.

**Why:** A browser driver submitted the first line while typing a multiline instruction, cleared the composer, and showed a local RUNNING state before its planned click. Authoritative native message counts remained empty and generation stayed idle. The local UI state alone did not prove an instruction reached the agent.

**How to apply:** Monitor submission evidence throughout text entry and cleanup. Do not close the customer page based solely on an unset click flag if keyboard submission may have started. If an input helper fails before any outbound instruction, distinguish that tooling failure from a genuinely unavailable customer editor; preserve all one-way checkpoints and reconcile activity before continuing.

Do not suspend a browser automation process that owns request interception to defer its cleanup. Its suspension also stops request continuation and can stall the customer page. Do not assume killing only the local observer preserves its browser child in a managed shell task.

**Why:** Suspending an observer left browser verification requests pending and made later UI samples unreliable. Terminating that observer also closed its managed browser, despite no direct browser signal. The production agent's independently persisted transcript remained available.

**How to apply:** Keep interception owners responsive and give browser cleanup a genuine lifecycle condition. If local tooling interferes, label the affected samples as infrastructure evidence, preserve single-send checkpoints, and recover the same authenticated profile without resending. Confirm a generated-app failure through normal bootstrap traffic, not through a synthetic API probe alone.
